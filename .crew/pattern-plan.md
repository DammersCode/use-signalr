CREW plan-track rules (read in full before planning; binding). The core rules are in the project CLAUDE.md.

REPO-TRUTH:
- From plan lock until "done", .crew/state.md is the source of truth and compaction-recovery state; the conversation is a cache. It and the other .crew/ work files (plan.md, rounds/, scratch/) stay out of git (.git/info/exclude, see setup.md) or are committed on a task branch; .crew/pattern.md, pattern-plan.md, templates.md, check.sh, lessons.md stay committed.
- Set PLAN "draft" when the plan track starts, so a compaction keeps the track. Update .crew/state.md with the state helper (not by rewriting the file) after plan lock, each step completion, each sidecar or lane state change.
- After any compaction, or when you cannot quote the current plan step or SIDE queue verbatim: re-read .crew/state.md, then reconcile: (a) SIDE against each recorded sidecar's branch (and against /tasks when the user pasted it) - a sidecar recorded running with no live subagent is re-verified from its worktree/branch (diff, tests, set done/issues, update SIDE) before any step-barrier decision; (b) the in-progress step against git status/diff (uncommitted changes are the step state). Continue from the step's criterion in .crew/plan.md, never from memory.
- Artifact check, same reconcile: re-derive a missing .crew/plan.md from NEXT + STATE (a plan change; G1 rule applies); a sidecar or lane entry lacking file list or branch gets its file list from git diff of its branch; no plan step starts while a running sidecar's file list is not on disk. Mismatches: max 5 lines, unasked; modes 1/2 wait for the user's go-ahead.
- Session start: an existing .crew/state.md with open NEXT, or uncommitted changes, is an earlier session's - report 1 line, ask before overwriting.

PLANNING (plan track):
- Step zero: identify needed skills (standing preferences, task type, named skills); record max 2 skills per step where applicable.
- PRIOR ART: before a size L step or a new mechanism, one scout searches GitHub/web for 2-3 permissively licensed projects that solved it; max 15 lines: repo@commit, technique, copy/avoid, licence. Ideas only; never paste code without a licence check. Result goes in .crew/plan.md next to the step.
- Plan = numbered list, written to .crew/plan.md. Header `SPEC: <file, issue, PR or earlier note that says what the work must do>` or `SPEC: none` (the TASK success criteria are then the SPEC lines). Each step lists its files and one completion criterion that quotes its SPEC line; done only when it holds. INSPECTOR brief and G3 name the SPEC; a change no SPEC line asks for is a finding.
- LOOP step (repeat-until work, e.g. review round - fix lane - merge - gates): its scope globs are its file list (in-scope fixes are planned: no replan, no G4 (b)); user-stated stop rule: until a clean round (0 must-fix) or max N rounds (STATE max rounds when set). The round cap is separate from the consult limit. Each round appends one line to .crew/rounds/log.md (templates.md); OPEN points to the last line. Convergence = new defects per round, not must-fix count.
- Before plan mode and on each re-entry: a limit message, or a /usage paste from the user (you cannot run it), shows the plan model near its limit: report 1 line, ask: wait / plan on mid tier (downgrade noted in OPEN) / re-scope to routine track. Never fall back silently.
- Plan model unavailable mid-plan (error, limit, fallback turn): stop, write the draft to .crew/plan.md marked "DRAFT", report 1 line, ask: wait / continue the draft on mid tier (noted in OPEN).
- PLAN CONFIRM (every mode, never the routine track): draft the plan (mode 1 with the user; modes 2 and 3 alone, G1 per GATES), then print the absolute path of .crew/plan.md in the user's OS format (C:\... on Windows, /... on Linux or macOS). It locks and work starts only after the user confirms it, also in mode 3; a mode 3 re-lock waits the same way (NEXT = "waiting: plan confirm").
- Replans: one window per task - batch all deviations, re-enter plan mode once. A scope change (steps added/removed/reordered, new files) re-triggers G1, counted against the cap; detail-only replans do not. Never re-plan informally in execution.

GATES - consult the BRAIN only at these triggers (one crisp question each, max 5 consults per task, budget priority G4 > G3 > G2 > G1). Log each consult with `consult G<n> <answer>`: the helper numbers it from the OPEN log on disk and refuses one past the limit.
G1 Before plan lock, only with at least one risk marker (new dependency, more than 5 steps, cross-module changes, data migration, external/paid API). Else self-check (each step one verifiable criterion? order sound? top 2 risks noted?), written as one 'self-check' line in .crew/plan.md (disk-verifiable), then straight to the user. Re-lock (replan, or plan re-derived after compaction): G1 only if the plan changed since the last review; not for unresolved gate failures (no successful review = no last review).
G2 Same error signature failed twice under the same fix approach (same failing test + assertion message, or same exception type + top stack frame): before the third attempt, ask root cause (not a patch) + alternative approach. Applies to sidecar fix loops too.
G3 Only if something changed since G1: plan re-locked, a G2 fired, or INSPECTOR returned ISSUES at least once. Bounded question: does the work meet every plan acceptance criterion? Top residual risks? No new diff review. Otherwise the full-diff INSPECTOR PASS alone clears "done".
G4 Before any decision that is (a) costly - expected over 30 minutes of compute, or uses a paid external resource (judge from the last comparable step; fixed threshold); (b) architectural - adds a third-party dependency, changes a public interface, or touches a file outside the plan's file list (globs and LOOP scope count as listed); a (b) decision on a step needing PRIOR ART waits for its line; (c) irreversible or security-relevant - destructive data operations, database migrations, force-push, branch deletion, git clean -x, auth/secret changes, any external side effect the user cannot undo. Batch one step's decisions into one consult. Irreversible actions also need the USER's explicit go-ahead before execution (mode 3: see MODES); the BRAIN advises on technical/cost tradeoffs only.
Log each consult in .crew/state.md OPEN, one line: gate, n/limit, short answer. Cap exhausted and a gate triggers: G4 - ask the user directly, never skip; G1/G2/G3 - own judgment, note "Gx skipped (cap)" in OPEN.
A BRAIN consult fails at any gate (unavailable, limit, error): stop the gated action, report which gate failed and why; user decides fix-and-rerun or proceed; record "Gn skipped: <reason>" in OPEN, the pending decision in ASK. Until that user decision is recorded: no re-lock, plan lock or "done" past the failed gate.

PARALLEL WORK (sidecar lanes):
- The main line (current plan step) never blocks on independent side findings.
- You decide, no advisor consult: a finding blocking the current step goes inline (error twice - G2). An independent finding disjoint from the active main line becomes a sidecar, fixed in the background while you continue. Disjoint = no main-line file imports a sidecar file and vice versa. Overlap, or disjointness uncertain: the sidecar waits in the queue, inline after the current step.
- A sidecar whose fix meets any G4 criterion is not dispatched before G4, counted against the task cap. Sidecar "Architectural" = changes a public interface or a file the main line imports.
- Step barrier: before each step, re-read SIDE from .crew/state.md and compare file lists. A running sidecar's files intersect the step's: the step does not start - wait for its completion + INSPECTOR PASS, or re-scope it inline and re-plan the step.
- Dispatch spec: name agent (sidecar, sidecar-complex, or sidecar-lite without a sandbox), model, effort, minimal tool set from the agent definition. Complex (multi-file, architectural): sidecar-complex with worktree isolation (own branch based on HEAD; setup sets worktree.baseRef: head). Sidecars never inherit the main session's model. Their permission prompts surface in the main session, visible to the user; dispatch prompt-prone sidecars at step start, not into user interaction.
- FIX LANE (sidecar or lane fixing findings; brief per templates.md, carrying the repo's own rules, e.g. AGENTS.md): a test added by the fix is shown failing before the fix; sibling sweep before reporting; no unrequested changes - a needed extra is a separate commit, listed in the report, reviewed on its own; a documented workaround or warning for a library trap becomes a code fix with a failing test.
- Routing check: after the session's first sidecar dispatch, ask the user for its /tasks row (modes 1/2; mode 3: log "routing unverified" in OPEN): served = expected model, mismatch - 1 line, stop it, handle inline. Early signal only; the task-end /usage check (ROUTING) stays authoritative. Repeat after any model or version change (mid-session limit, /model, update).
- Lifecycle: queued / running / done / issues / verified, stored only in .crew/state.md SIDE, updated on every transition, read from disk before any status claim. "issues" = INSPECTOR ISSUES or merge conflict: redispatch a fix (same model) or handle inline after the current step; "issues" blocks G3 like "running". Only you set "verified", after INSPECTOR PASS on the sidecar diff. Circuit breaker: 3 consecutive hook exit-2 blocks on one sidecar halt it (status issues), escalate to ASK, no retry loop. Lanes follow the same rules.
- Instances: several machines or sessions may work in parallel, each with own worktree and branch (lane entry with host). Plain push to its work branch after a fetch; resolve conflicts between instances by merging the work branch (rebase only unpushed commits); never force.
- Pre-merge file check: before merging a worktree sidecar, derive its actual file set from git diff (branch vs. base commit) and compare to the SIDE list; any file outside it = out-of-scope mismatch - stop and ask the user, never a blind merge.
- Merge a sidecar branch only after INSPECTOR PASS on its diff; a long-lived branch (lane) also runs the full local check set once before it becomes a merge parent. Merge conflict: status "issues"; the PILOT resolves it on the main branch in a separate commit; then normal sidecar inspection; resolution deviates from the sidecar's reported intent - re-scope and re-plan per step barrier.
- Sidecar final report: max 10 lines (files changed, test output summary, deviations, commit hash). Reviewers and probers write the full report to .crew/rounds/ and return only must-fix + counts + file path.
- Max 2 active sidecars: before every dispatch read SIDE from disk, count active entries (queued/running/issues); at 2 or more the new one waits in the queue. The hand-off rule (scout rules: roughly 1,500 tokens of mechanical work) applies to sidecars too.
- G3 precondition: no open sidecars before "done". DONE-CHECKLIST: re-read .crew/state.md from disk, verify (1) every sidecar entry = verified; (2) inspector PASS recorded for the main line and each sidecar diff; (3) no task-touched file (plan file list + STATE) uncommitted - it blocks done until committed or the user decides; files outside the task's set and git-excluded work files are not task files (report in 1 line, not blocking); (4) consult log complete within the limit, state.md within 40 lines; (5) SKILLS consistent: max 2 skills per step, no dropped skill loaded; (6) final score: one full-diff review against the repo's rules found no must-fix. CI backstop: the repo's required CI checks green on the last commit before "done" (no CI - one line "no CI" in VERIFY; CI that runs only on pull requests never turns green on a branch push: VERIFY says "CI pending PR" and done rests on green local checks; gate lists come from the repo's rules - AGENTS.md, CLAUDE.md, CI config - never from memory). Report "done" with checks quoted; any failed check = not done.
- CLEANUP (after "done", setup.md C2): remove this task's clean, merged worktrees, then its scratch files and logs; the rest goes to ASK.
- PUBLISH (after DONE-CHECKLIST): record the top-level target (tag, release, default-branch push or merge) in STATE as the user states it; prepare the exact command, hand it over in 1 line; the user runs it (the guard hook blocks you).

SKILLS (step zero + task-scoped loading):
- Load a skill only when the step needs it; for delegated work the subagent loads it, never the main session.
- Loaded skill rules are binding: the step's criterion includes the skill's checks.
- Standing user preferences live in the .crew/state.md SKILLS section and survive every task and compaction.
- Drop loop: PLANNER, BRAIN or you (in execution) flag a loaded skill that proves unnecessary or counterproductive; the flag is a material event, shown unasked (max 3 lines: skill, reason, effect); the user decides; record the drop with reason in SKILLS. Dropped skills stay dropped until the user reinstates them.

CONTEXT BUDGET:
- 1 task = 1 session. Before any gate AND each new plan step: the context is near ~50 % of the model window (the user's statusline or a harness warning tells you) - update .crew/state.md, compact at that boundary (modes 1/2: 1 line asking the user to run /compact; AFK: continue, the harness compacts), recover per REPO-TRUTH.
- Harness auto-compaction: reconcile per REPO-TRUTH before the next action, log it in OPEN. No statusline: in modes 1/2 ask the user to check /context when the session is long; mode 3 relies on the harness compaction.
- Execution model hits a limit mid-task: stop with .crew/state.md current, report 1 line, continue after the reset; never a silent fallback. Stopped subagents lose no findings (reports on disk in .crew/rounds/); continue them with SendMessage after the reset.
- /compact only at natural breaks (step boundaries, between tracks), never mid-step. Before plan lock / model switch: main context holds only the plan plus citations. Large file reads go to SCOUTS (within the scout output cap).

ROUTING: you cannot run /tasks or /usage, the user can. Verify routing with the user's /tasks paste (model and effort per subagent row) and, at task end, the user's /usage attribution against the expected model mix; without a paste, log "routing unverified" in OPEN. After any Claude Code update, re-run the setup check before delegating. The UI may show the requested model, not the served one (Issue #43869); attribution is the stronger signal.
